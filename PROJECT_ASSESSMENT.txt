ATHENA PROJECT ASSESSMENT
Generated: 2026-08-10

OVERVIEW

Athena (formerly Jarvis) is a local-first Windows AI assistant. It combines
voice, tray/dashboard UI, local Ollama-based planning, deterministic tools,
permission checks, RAG memory, monitoring, and optional OpenClaw execution.
The architecture is thoughtfully separated and well documented, but execution
policy enforcement, testability, and repository hygiene need attention.

ARCHITECTURE

Primary flow:
  Voice / Text / Tray UI
    -> core orchestrator and planner
    -> RAG, session context, and Ollama
    -> tool registry and permission checks
    -> executor and verification
    -> Windows applications, files, browser, terminal, data, and email tools

Major areas:
  - brain/: intent routing, prompting, LLM client, action parsing
  - core/: orchestration, planning facade, missions, task management, events
  - tools/: application, browser, filesystem, terminal, development, email,
    data-engineering, vision, and system capabilities
  - security/: risk classification, permissions, audit, sanitization, paths
  - rag/ and memory/: document retrieval, vector store, session/workflow memory
  - voice/, ui/, monitoring/: user interaction and runtime observability

STRENGTHS

  - Clear subsystem boundaries and an understandable end-to-end design.
  - Tool calls are validated against a registry before execution.
  - Path guarding protects common Windows system locations for destructive file
    operations.
  - High-risk deletion and email actions have confirmation requirements.
  - Post-action verification, task tracking, audit events, health checks, and
    PyInstaller packaging are already present.
  - Documentation covers installation, architecture, security, tools, RAG,
    voice, vision, packaging, and troubleshooting.

FINDINGS

1. HIGH: Medium-risk confirmation policy is not loaded from permissions.yaml

  config/permissions.yaml sets confirm_medium_risk: true, but Settings loads
  policy values from .env/defaults rather than this YAML. The runtime default
  for confirm_medium_risk is false. As a result, medium-risk operations can run
  without confirmation despite the project configuration indicating otherwise.

  Impact: LLM-generated plans can invoke medium-risk tools without an approval
  prompt. This includes terminal command tools.

  Relevant files:
    config/settings.py
    config/permissions.yaml
    security/permissions.py
    tools/terminal_tools.py

2. HIGH: Plan execution does not apply permission denials

  executor/plan_executor.py checks only whether a tool requires confirmation,
  then calls execute_action(). It does not call evaluate_permission() or stop
  execution when a decision is denied. Therefore a future CRITICAL tool would
  not be reliably denied by the plan-execution path, despite the intended
  deny-critical-by-default policy.

  Relevant files:
    executor/plan_executor.py
    security/permissions.py
    permissions/permissions.py

3. HIGH: Arbitrary shell execution is exposed as medium risk

  run_cmd_command uses subprocess.run(..., shell=True), and the PowerShell tool
  passes arbitrary commands to powershell -Command. These tools rely entirely
  on the confirmation policy above, which currently defaults to no medium-risk
  confirmation unless an environment variable overrides it.

  Relevant files:
    tools/terminal_tools.py
    security/risk.py

4. MEDIUM: Test discovery configuration does not match the test directory

  pyproject.toml specifies testpaths = ["tests"], while the repository uses the
  directory name Tests. A normal pytest invocation will not reliably collect
  the intended suite.

  Relevant file:
    pyproject.toml

5. MEDIUM: Local Python environment is broken

  .venv/pyvenv.cfg points to a Python 3.12 interpreter that is absent on the
  machine. The venv interpreter and pytest launcher cannot start, so automated
  compilation and test execution could not be performed during this review.
  Recreate .venv with an installed Python 3.12+ interpreter before validating
  the project.

6. MEDIUM: Git ownership is unclear

  Git resolves to D:/Projects rather than D:/Projects/Jarvis, and the Jarvis
  directory currently appears as untracked content in that parent repository.
  This prevents reliable project-level history, code review, and release
  traceability.

7. MEDIUM: Optional tool-subsystem failures are silent

  tools/bootstrap.py broadly catches exceptions while registering optional
  subsystem tools, generally without logging. A missing dependency can quietly
  remove a capability from the registry and planner.

RECOMMENDED PRIORITY ORDER

  1. In execute_plan(), evaluate permission decisions and stop immediately when
     a tool is denied.
  2. Make permissions.yaml authoritative for policy settings, or remove those
     unused values and document .env as the only source of truth.
  3. Require confirmation for arbitrary CMD and PowerShell commands by default;
     consider a stricter allowlist or constrained command interface.
  4. Align test discovery by renaming Tests to tests or updating pyproject.toml.
  5. Recreate .venv, install dependencies, and run the full test suite.
  6. Establish D:/Projects/Jarvis as an independently tracked Git repository,
     or explicitly include it in the parent repository.
  7. Log optional tool-registration failures with the missing capability and
     root exception.

CONCLUSION

Athena has a strong foundation for a local desktop agent. Before expanding
capabilities, prioritize a single consistently enforced execution policy and a
reproducible test environment. Those two changes will materially improve the
project's safety and maintainability.
